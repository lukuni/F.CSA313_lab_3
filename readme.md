## Алхам 2: Чанарын сценариоуд (6 хэсэгтэй)

### 1. Performance сценарио — `/cart/add`

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэрэглэгч бараагаа сагсанд нэмэхэд систем хэвийн ачаалалд хурдан хариу өгөх ёстой. |
| **Системийн төлөв** | Express сервер энгийн horizontal scaling-гүй, ганц процессоор `localhost:3000` дээр ажиллаж байна. |
| **Орчны төлөв** | 20 зэрэгцээ хэрэглэгч (VU) тогтмол ачаалал үүсгэж байна; сүлжээний саатал байхгүй (локал сервер). |
| **Гадаад өдөөлт** | Хэрэглэгч `POST /cart/add` хүсэлт илгээв. |
| **Шаардлагатай хариу** | Сервер `{ ok: true, items: 1 }` гэсэн JSON-г 200 статустай хурдан буцаана. |
| **Хэмжүүр** | 20 VU-ийн тогтмол ачаалалд, 1 минутын турш, хариу хугацааны **p95 < [XXX] мс**. |

### 2. Reliability сценарио — `/pay`

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэрэглэгч төлбөрөө хийхэд систем ихэнх тохиолдолд амжилттай гүйцэтгэх ёстой; санамсаргүй backend алдаа гарах магадлал бий. |
| **Системийн төлөв** | `/pay` endpoint дотоод логикоороо ~5% магадлалтайгаар 500 (gateway timeout) алдаа буцаадаг байдлаар зохион байгуулагдсан. |
| **Орчны төлөв** | 20 VU, 1 минутын турш тогтмол ачаалал; сервер нормал ажиллагаатай (унаагүй). |
| **Гадаад өдөөлт** | Хэрэглэгч `POST /pay` хүсэлт илгээж төлбөрөө хийхийг оролдов. |
| **Шаардлагатай хариу** | Ихэнх тохиолдолд `{ paid: true }` 200 статустай буцна; алдааны хувь тодорхой хязгаараас хэтрэхгүй байх ёстой. |
| **Хэмжүүр** | 20 VU, 1 минутын цонхонд `/pay`-ийн **error rate (POFOD) < 8%**. |

### 3. Availability сценарио — сервер эвдрэл ба сэргэлт

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Сервер гэнэт унасан тохиолдолд систем удаан хугацаанд хэрэглэгчдэд хүрэлцээгүй байж болохгүй — түргэн сэргэх ёстой. |
| **Системийн төлөв** | Ганц instance-тэй, автомат redundancy/failover-гүй Express сервер. |
| **Орчны төлөв** | 10 VU, 2 минутын турш ачаалал өгч байх үед серверийг зориудаар 10 секундын турш зогсоосон (chaos тест). |
| **Гадаад өдөөлт** | Процесс crash хийж (`Ctrl+C`), 10 секундын дараа дахин асаав. |
| **Шаардлагатай хариу** | Зогсолтын үед ирсэн хүсэлтүүд алдаатай (connection refused) буцах ч, сервер дахин асахтай зэрэгцэн шинэ хүсэлтүүд амжилттай хариу авах ёстой. |
| **Хэмжүүр** | 2 минутын цонхонд нийт хүсэлтийн амжилтын хувиар тооцсон **availability ≥ 90%**; серверийн сэргэх хугацаа (recovery time) ≤ 10с. |

## Алхам 3: SLO хүснэгт (SLI, босго, цонх) + үндэслэл + error budget тооцоо

Доорх босгуудыг зааврын жишээ тоог шууд хуулахгүйгээр, `/cart/add` болон `/pay`-д хийсэн bodит baseline хэмжилт дээр үндэслэн гаргав (baseline скрипт болон гаралт: `baseline-cart.js`, `baseline-pay.js`, `results/baseline-cart.txt`, `results/baseline-pay.txt`).

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | Үндэслэл |
|---|---|---|---|---|
| Performance | `/cart/add` latency | **p(95) < 28ms** | 20 VU тогтмол ачаалалд, 1 мин | Baseline хэмжилт: p95 = 18.58ms. 18.58 × 1.5 ≈ 27.9 → 28ms-д дугуйруулав (үйлдвэрлэлийн ачаалал нэмэгдэхэд зохистой зөвшөөрөл өгөх зорилготой) |
| Reliability | `/pay` error rate | **rate < 0.08 (8%)** | 20 VU, 1 мин | Baseline хэмжилт: error rate = 4.66% (56/1200 хүсэлт). 4.66% × ~1.6 ≈ 7.5% → 8%-д дугуйруулав |
| Availability | Нийт хүсэлтийн амжилтын хувь | **≥ 90%** | 10 VU, 2 мин, дунд нь 10с сервер зогссон | Сервер богино хугацаанд унасан ч 2 минутын цонхонд нийт хүсэлтийн 90%-иас доошгүй хувь нь амжилттай байх ёстой гэсэн бизнесийн шаардлагаас гаргав |

### Error budget тооцоо (цагаар)

- Цонх = 2 минут = 120 секунд
- SLO = 90% availability
- **Budget = 120 × (1 − 0.90) = 12 секунд** — энэ хугацаанд систем "эвдэрсэн" байж болно гэсэн онолын зөвшөөрөл

> Энэ бол зөвхөн ЦАГААР тооцсон budget. Алхам 5-т chaos тест хийсний дараа үүнийг ХҮСЭЛТЭЭР дахин тооцож, хоёр тоо яагаад ялгаатай гарч байгааг доор тайлбарлана (сервер унасан үед хүсэлтүүд агшин зуур connection refused буцдаг тул нэг секундэд хэвийнээс олон хүсэлт "иддэг").

## Алхам 4: SLO-г k6 threshold болгох

`slo-test.js` скрипт нь `/cart/add`, `/report`, `/pay` гурван endpoint-ийг `name` tag-аар ялгаж, тус бүрд нь Алхам 3-т тогтоосон босготой яг ижил утгаар threshold тавьсан:

```js
export const options = {
  vus: 20,
  duration: '1m',
  thresholds: {
    'http_req_duration{name:cart}':   ['p(95)<28'],    // Performance SLO
    'http_req_failed{name:pay}':      ['rate<0.08'],   // Reliability SLO
    'checks':                         ['rate>0.90'],   // Availability SLO
    'http_req_duration{name:report}': ['p(95)<450'],   // Report SLO (нэмэлт, 4 дэх)
  },
};
```

Ажиллуулах команд: `k6 run slo-test.js 2>&1 | tee results/pass.txt`

### PASS гаралтын хураангуй (`results/pass.txt`)

| Threshold | Заалт | Бодит утга | Үр дүн |
|---|---|---|---|
| Performance (`cart`) | p(95) < 28ms | p95 = 1.85ms | ✓ PASS |
| Report (нэмэлт) | p(95) < 450ms | p95 = 390.22ms | ✓ PASS |
| Reliability (`pay`) | rate < 0.08 | rate = 4.19% | ✓ PASS |
| Availability (`checks`) | rate > 0.90 | rate = 98.60% | ✓ PASS |

Бүх 4 threshold ✓ PASS гарсан. `checks_failed` 1.39% (39/2790) бүхэлдээ `/pay`-ийн санамсаргүй 500 алдаанаас үүдэлтэй (`pay` check: 891/930 ✓ — энэ нь 4.19% error rate-тэй тохирч байна).
