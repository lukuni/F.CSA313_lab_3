## Алхам 2: Чанарын сценариоуд (6 хэсэгтэй)

### 1. Performance сценарио — `/cart/add`

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэрэглэгч бараагаа сагсанд нэмэхэд систем хэвийн ачаалалд хурдан хариу өгөх ёстой. |
| **Системийн төлөв** | Express сервер энгийн horizontal scaling-гүй, ганц процессоор `localhost:3000` дээр ажиллаж байна. |
| **Орчны төлөв** | 20 зэрэгцээ хэрэглэгч (VU) тогтмол ачаалал үүсгэж байна; сүлжээний саатал байхгүй (локал сервер). |
| **Гадаад өдөөлт** | Хэрэглэгч `POST /cart/add` хүсэлт илгээв. |
| **Шаардлагатай хариу** | Сервер `{ ok: true, items: 1 }` гэсэн JSON-г 200 статустай хурдан буцаана. |
| **Хэмжүүр** | 20 VU-ийн тогтмол ачаалалд, 1 минутын турш, хариу хугацааны **p95 < [XXX] мс**. |

### 2. Reliability сценарио — `/pay`

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэрэглэгч төлбөрөө хийхэд систем ихэнх тохиолдолд амжилттай гүйцэтгэх ёстой; санамсаргүй backend алдаа гарах магадлал бий. |
| **Системийн төлөв** | `/pay` endpoint дотоод логикоороо ~5% магадлалтайгаар 500 (gateway timeout) алдаа буцаадаг байдлаар зохион байгуулагдсан. |
| **Орчны төлөв** | 20 VU, 1 минутын турш тогтмол ачаалал; сервер нормал ажиллагаатай (унаагүй). |
| **Гадаад өдөөлт** | Хэрэглэгч `POST /pay` хүсэлт илгээж төлбөрөө хийхийг оролдов. |
| **Шаардлагатай хариу** | Ихэнх тохиолдолд `{ paid: true }` 200 статустай буцна; алдааны хувь тодорхой хязгаараас хэтрэхгүй байх ёстой. |
| **Хэмжүүр** | 20 VU, 1 минутын цонхонд `/pay`-ийн **error rate (POFOD) < 8%**. |

### 3. Availability сценарио — сервер эвдрэл ба сэргэлт

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Сервер гэнэт унасан тохиолдолд систем удаан хугацаанд хэрэглэгчдэд хүрэлцээгүй байж болохгүй — түргэн сэргэх ёстой. |
| **Системийн төлөв** | Ганц instance-тэй, автомат redundancy/failover-гүй Express сервер. |
| **Орчны төлөв** | 10 VU, 2 минутын турш ачаалал өгч байх үед серверийг зориудаар 10 секундын турш зогсоосон (chaos тест). |
| **Гадаад өдөөлт** | Процесс crash хийж (`Ctrl+C`), 10 секундын дараа дахин асаав. |
| **Шаардлагатай хариу** | Зогсолтын үед ирсэн хүсэлтүүд алдаатай (connection refused) буцах ч, сервер дахин асахтай зэрэгцэн шинэ хүсэлтүүд амжилттай хариу авах ёстой. |
| **Хэмжүүр** | 2 минутын цонхонд нийт хүсэлтийн амжилтын хувиар тооцсон **availability ≥ 90%**; серверийн сэргэх хугацаа (recovery time) ≤ 10с. |
