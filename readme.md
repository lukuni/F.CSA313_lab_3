## Алхам 3: SLO хүснэгт (SLI, босго, цонх) + үндэслэл + error budget тооцоо

Доорх босгуудыг зааврын жишээ тоог шууд хуулахгүйгээр, `/cart/add` болон `/pay`-д хийсэн bodит baseline хэмжилт дээр үндэслэн гаргав (baseline скрипт болон гаралт: `baseline-cart.js`, `baseline-pay.js`, `results/baseline-cart.txt`, `results/baseline-pay.txt`).

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | Үндэслэл |
|---|---|---|---|---|
| Performance | `/cart/add` latency | **p(95) < 28ms** | 20 VU тогтмол ачаалалд, 1 мин | Baseline хэмжилт: p95 = 18.58ms. 18.58 × 1.5 ≈ 27.9 → 28ms-д дугуйруулав (үйлдвэрлэлийн ачаалал нэмэгдэхэд зохистой зөвшөөрөл өгөх зорилготой) |
| Reliability | `/pay` error rate | **rate < 0.08 (8%)** | 20 VU, 1 мин | Baseline хэмжилт: error rate = 4.66% (56/1200 хүсэлт). 4.66% × ~1.6 ≈ 7.5% → 8%-д дугуйруулав |
| Availability | Нийт хүсэлтийн амжилтын хувь | **≥ 90%** | 10 VU, 2 мин, дунд нь 10с сервер зогссон | Сервер богино хугацаанд унасан ч 2 минутын цонхонд нийт хүсэлтийн 90%-иас доошгүй хувь нь амжилттай байх ёстой гэсэн бизнесийн шаардлагаас гаргав |

### Error budget тооцоо (цагаар)

- Цонх = 2 минут = 120 секунд
- SLO = 90% availability
- **Budget = 120 × (1 − 0.90) = 12 секунд** — энэ хугацаанд систем "эвдэрсэн" байж болно гэсэн онолын зөвшөөрөл

> Энэ бол зөвхөн ЦАГААР тооцсон budget. Алхам 5-т chaos тест хийсний дараа үүнийг ХҮСЭЛТЭЭР дахин тооцож, хоёр тоо яагаад ялгаатай гарч байгааг доор тайлбарлана (сервер унасан үед хүсэлтүүд агшин зуур connection refused буцдаг тул нэг секундэд хэвийнээс олон хүсэлт "иддэг").

## Алхам 4: SLO-г k6 threshold болгох

`slo-test.js` скрипт нь `/cart/add`, `/report`, `/pay` гурван endpoint-ийг `name` tag-аар ялгаж, тус бүрд нь Алхам 3-т тогтоосон босготой яг ижил утгаар threshold тавьсан:

```js
export const options = {
  vus: 20,
  duration: '1m',
  thresholds: {
    'http_req_duration{name:cart}':   ['p(95)<28'],    // Performance SLO
    'http_req_failed{name:pay}':      ['rate<0.08'],   // Reliability SLO
    'checks':                         ['rate>0.90'],   // Availability SLO
    'http_req_duration{name:report}': ['p(95)<450'],   // Report SLO (нэмэлт, 4 дэх)
  },
};
```

Ажиллуулах команд: `k6 run slo-test.js 2>&1 | tee results/pass.txt`

### PASS гаралтын хураангуй (`results/pass.txt`)

| Threshold | Заалт | Бодит утга | Үр дүн |
|---|---|---|---|
| Performance (`cart`) | p(95) < 28ms | p95 = 1.85ms | ✓ PASS |
| Report (нэмэлт) | p(95) < 450ms | p95 = 390.22ms | ✓ PASS |
| Reliability (`pay`) | rate < 0.08 | rate = 4.19% | ✓ PASS |
| Availability (`checks`) | rate > 0.90 | rate = 98.60% | ✓ PASS |

Бүх 4 threshold ✓ PASS гарсан. `checks_failed` 1.39% (39/2790) бүхэлдээ `/pay`-ийн санамсаргүй 500 алдаанаас үүдэлтэй (`pay` check: 891/930 ✓ — энэ нь 4.19% error rate-тэй тохирч байна).

## Алхам 5: Мини chaos — availability сценариог турших

`slo-test.js`-ийг 2 минутын турш ажиллуулж байх зуур сервер (`node server.js`) дунд нь зориудаар зогсоож (`Ctrl+C`), ~10 секундын дараа дахин асаав. Command: `k6 run slo-test.js --duration 2m 2>&1 | tee results/chaos.txt`

### Threshold-ийн үр дүн

| Threshold | Заалт | Бодит утга | Үр дүн |
|---|---|---|---|
| Availability (`checks`) | rate > 0.90 | rate = **67.33%** | ✗ FAIL |
| Reliability (`pay`) | rate < 0.08 | rate = **34.75%** | ✗ FAIL |
| Performance (`cart`) | p(95) < 28ms | p95 = 1.81ms | ✓ PASS |
| Report (нэмэлт) | p(95) < 450ms | p95 = 386.46ms | ✓ PASS |

Chaos тестийн үед нийт 5991 хүсэлтийн 1957 (32.66%) нь амжилтгүй болов; тестийн зогсолтын хугацаанд ирсэн хүсэлтүүд бараг бүгд алдаатай буцав.

### Цагаар vs хүсэлтээр тооцсон availability — яагаад зөрдөг вэ

Алхам 3-т ЦАГААР тооцсон error budget: 120с × (1−0.90) = **12 секунд**.

Бодит ХҮСЭЛТЭЭР тооцсон budget-ийн хэтрэлт:
- Нийт хүсэлт: 5991, Failed: 1957 (32.66%)
- 90% SLO-д зөвшөөрөгдөх failed хүсэлтийн тоо: 5991 × 10% ≈ 599
- Бодит failed 1957 → зөвшөөрөгдөх хэмжээгээ **~3.3 дахин хэтрүүлсэн**

Зөрүүний шалтгаан: сервер зогссон үед хүсэлт бүр шууд (connection refused) буцдаг тул нэг iteration маш хурдан дуусаж дараагийн хүсэлт рүү шилждэг; харин хэвийн үед `/report`-ийн 200–400мс хүлээлт + `sleep(1)` зэргээс болж нэг iteration ойролцоогоор 1.2–1.4с үргэлжилдэг. Иймд зогсолтын **нэг цаг хугацааны секунд** дотор хэвийн үеийнхээс хамаагүй олон хүсэлт "багтдаг" тул хүсэлтээр тооцсон алдаа цагаар тооцсоноос хамаагүй өндөр гарна.

### Reliability threshold яагаад мөн FAIL болов

Сервер бүхэлдээ унасан үед `/pay`-ийн хүсэлт бүр л амжилтгүй болдог тул нэг эвдрэл (crash) **availability болон reliability хоёр SLO-г зэрэг зөрчдөг** — учир нь хоёр SLI хоёулаа нэг л дундын шалтгаан (сервер унасан эсэх)-аас хамааралтай. Хэрэв SLI-үүдээ бие даасан болгож ялгах бол: availability-г зөвхөн health-check endpoint (жишээ нь `/health`)-ийн амжилтын хувиар, reliability-г зөвхөн серверийн доторх бизнес-логикийн алдаа (жишээ нь `/pay`-ийн 5% санамсаргүй алдаа, сервер асаалттай үед)-оор тусад нь хэмжвэл crash-ийн нөлөө хоёр хэмжүүрт зэрэг тусахгүй болно.

## Алхам 6: Threshold-оо зориудаар эвдэх

`slo-test-fail.js` нь `slo-test.js`-ийн хуулбар бөгөөд зөвхөн `report` threshold-ыг `p(95)<450` → **`p(95)<100`** болгож хатууруулсан. Сервер `/report`-д хэзээ ч 200мс-ээс хурдан хариулдаггүй тул энэ FAIL нь ямар ч машин дээр найдвартай давтагдана.

Command: `k6 run slo-test-fail.js 2>&1 | tee results/fail.txt`

### Үр дүн

| Threshold | Заалт | Бодит утга | Үр дүн |
|---|---|---|---|
| Report | p(95) < 100ms | p95 = 389.53ms | ✗ **FAIL** |
| Availability (`checks`) | rate > 0.90 | rate = 98.66% | ✓ PASS |
| Reliability (`pay`) | rate < 0.08 | rate = 3.99% | ✓ PASS |
| Performance (`cart`) | p(95) < 28ms | p95 = 2.52ms | ✓ PASS |

k6-ийн гаралтад `THRESHOLDS` хэсгийн `http_req_duration{name:report}` мөрийн эсрэг талд `✗` тэмдэг гарч, доор нь `level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"` гэсэн мэдэгдэл хэвлэгдэв.

### Exit code — CI/CD-д чухал ажиглалт

Эхэндээ `echo "exit=$?"` ашигласан боловч энэ нь **`tee`**-ийн exit code-ыг буцаадаг (учир нь `$?` нь pipe-ийн хамгийн сүүлийн командын статусыг л авдаг), k6-ийнх биш. Зөв exit code авахын тулд Mac дээрх **zsh** shell-д зориулж:

```bash
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt
echo "exit=${pipestatus[1]}"
```

(bash дээр `${PIPESTATUS[0]}` ашиглана, zsh дээр `${pipestatus[1]}` — индекс 1-ээс эхэлдэг.)

Ингэж засварласны дараа **`exit=99`** гарсан — энэ бол k6-ийн threshold зөрчигдсөн үеийн стандарт exit code бөгөөд яг үүгээр CI pipeline build-ээ зогсоодог. Хэрэв `tee`-той pipe хийхдээ exit code-оо анхаарахгүй бол CI дээр FAIL-ийг PASS мэт андуурч болзошгүй гэдгийг энэ туршилтаас ойлгов.

## Дүгнэлт

Сценарио → SLO → threshold шилжилтэд хамгийн хэцүү зүйл нь тоог "зохион гаргах" биш, **бодит baseline хэмжилт дээр үндэслэх** байсан — эхлээд зааврын жишээ тоог (жишээ нь p(95)<300) шууд ашиглах уруу татагдаж байсан ч, `/cart/add`-ын бодит baseline (p95=18.58ms) хэмжсэний дараа тэр тоо манай системд огт хамааралгүй болохыг ойлгов. Хоёр дахь хэцүү тал нь `README.md`-ийн SLO хүснэгт дэх тоо болон `slo-test.js`-ийн `thresholds` доторх тоо **яг ижил байх ёстой** гэдэг шаардлага байсан — эхлээд харилцан адилгүй байсныг олж, засах шаардлагатай болсон. Chaos туршилтын хэсэгт `${PIPESTATUS[0]}` bash-д зориулагдсан бол миний Mac дээрх zsh дээр огт ажиллахгүй байсан нь k6-тай шууд холбоогүй ч практик shell-ийн ялгааг ойлгох хэрэгтэй болгосон.

Chaos туршилт availability сценариогийн хэмжүүрийг **батлахаас илүү бодит эрсдэлийг илчилсэн** гэж хэлж болно: тестийн өмнө availability SLO (≥90%) хэвийн ачаалалд амархан хангагдана гэж таамагласан ч, 10 секундын зогсолт ердөө нэгээхэн удаа тохиолдоход availability 67.33% болтлоо унасан нь SLO-г маш их зөрчсөн. Түүнчлэн ЦАГААР тооцсон 12 секундын error budget-той харьцуулахад ХҮСЭЛТЭЭР тооцсон бодит хэтрэлт ~3.3 дахин их байсан нь availability-г зөвхөн хугацаагаар дүгнэх нь хангалтгүй болохыг харуулсан — систем маш богино хугацаанд ч унасан бол хэрэглэгчийн туршлагад үзүүлэх нөлөө хугацааны пропорциос хамаагүй хүчтэй байж болно. Мөн нэг эвдрэл (сервер crash) availability болон reliability хоёр SLO-г зэрэг унагаасан нь эдгээр хэмжүүрүүд бие биенээсээ бүрэн тусгаарлагдаагүй байсныг харуулсан бөгөөд ирээдүйд SLI-гээ тусад нь (жишээ нь availability-г health-check-ээр, reliability-г зөвхөн бизнес-логикийн алдаагаар) тодорхойлох нь илүү зөв дүн шинжилгээ өгнө гэж дүгнэлээ.

Ерөнхийдөө энэ лаб намайг лекцийн онолын ойлголт болох "SLO бол таамгаар биш, бодит хэмжилт дээр үндэслэсэн байх ёстой" гэдгийг практикт мэдрэхэд тусалсан — учир нь baseline хэмжилтгүйгээр SLO гаргасан бол availability threshold маань хэдэн ч хамааралгүй тоо байх байсан. FAIL хувилбарыг зориудаар гаргаж, exit code-ыг зөв авахад тулгарсан bash/zsh-ийн ялгаа нь CI pipeline бодит нөхцөлд яагаад ийм нарийн зүйлд бас анхаарал хандуулах шаардлагатайг харуулсан.

## Нэмэлт даалгавар (AI өнцөг)

`server.js`-ийн кодыг өгөөд "6 хэсэгтэй форматаар 3 чанарын сценарио бич" гэж AI туслахаас (Claude) хүссэн. Гарсан хариултыг "сайн сценариогийн 5 шинж" (итгэмжтэй, үнэ цэнэтэй, тодорхой, нарийн, ойлгомжтой)-ээр шүүж, өөрийн бичсэнтэй харьцуулав.

**(1) AI-ийн санал болгосон тоон босго бодитой байсан уу?:** AI зөвхөн кодыг харж, ажиллуулаагүй тул тоон босгыг **баримт бус таамаг**-аар өгсөн — жишээ нь availability-д "99.9% uptime" гэсэн ердийн үйлдвэрлэлийн SLA тоог санал болгосон нь манай 2 минутын chaos тестийн context-д (10 секундын зогсолттой үед) огт биелэшгүй, утга учиргүй босго байсан. Харин бид `/cart/add`-ыг бодитоор ачаалж (baseline p95=18.58ms) хэмжсэний дараа AI-ийн санал болгосон "ерөнхий latency SLO" биш, endpoint тус бүрд тусгайлсан, хэмжсэн тоон дээр суурилсан босго гаргасан — энэ нь "нарийн" гэсэн шинжид илүү нийцнэ.

**(2) AI ямар өдөөлтийг мартсан эсвэл зохиосон бэ?:** AI `/report` endpoint-ийг сценариондоо тусад нь авч үзээгүй — гурван endpoint-ийн зөвхөн хоёрыг (cart, pay) голчлон дурдаж, удаан хариу өгдөг `/report`-ийн онцлогийг орхигдуулсан. Мөн Availability сценарионд "сервер crash" гэсэн ерөнхий тайлбар өгсөн ч, **хэдэн секунд зогсох, хэзээ сэргэх** гэсэн тодорхой нөхцөл (which is required for "тодорхой" trait) зохиогоогүй — зөвхөн бидний өгсөн context (`Ctrl+C`, 10с зогсолт) байсны дараа тодорхой болсон.

**(3) Өөрийн бичсэнтэй харьцуулахад юу нь дээр, юу нь дутуу байсан бэ?:** Манай өөрийн бичсэн сценарио дараах давуу талтай байсан — endpoint бүрийг тусад нь тодорхой авч үзсэн, тоон босгыг бодит baseline хэмжилт дээр үндэслэсэн, chaos тестийн нөхцөлийг (10с зогсолт) тодорхой заасан. Харин AI-ийн давуу тал нь — **6 хэсгийн бүтцийг маш хурдан, зөв форматаар гаргаж өгсөн** бөгөөд Тойм, Системийн төлөв гэх мэт хэсгүүдийн уялдааг сайн барьсан; манай анхны ноорог дээр ч энэ бүтэц AI-ийн санал болгосон загвартай төстэй байсан нь AI-ийг эхний drafting шатанд ашиглах нь цаг хэмнэдэг гэдгийг харуулсан. Ерөнхийдөө AI бол сценарионы **бүтэц, хэлбэрийг хурдан гаргахад тустай**, харин **тоон утга, context-specific нарийн ширийн зүйлд** заавал хүний (эсвэл бодит хэмжилтийн) баталгаажуулалт хэрэгтэй гэдгийг энэ дасгал харуулав.
